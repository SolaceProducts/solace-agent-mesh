# Event-mesh entrypoint (GA)

Turns Solace broker messages into agent or workflow tasks, and optionally publishes the results back to the mesh. This is the **trigger half** of "listen → filter → store": the entrypoint fires the task, optionally after a rule's `eventFilter` has dropped the messages not worth a task; branching logic and multi-step processing belong in a workflow (`sam-author-agent`), which an event rule can target directly. The reverse direction — an *agent* sending requests onto the mesh as a tool — is the `event_mesh` **connector** (`sam-connectors`).

Field names below are real keys for recognition; full YAML belongs to `sam-declarative-config` (or pull a UI-created entrypoint). In the builder UI, event rules have a dedicated editor, not a generic form.

## Broker connection

Point the entrypoint at the event-source broker with explicit details: `broker_url` (`tcp/tcps/ws/wss`), `broker_vpn`, `broker_username`, `broker_password`, `tls_skip_verify` (leave `false` outside dev). Leaving `broker_url` empty falls back to the local dev broker only when no broker URL resolves at all (the runtime keys off that, not off an "is this embedded/desktop" check). A deployed entrypoint still needs real broker details: whenever the platform has a system broker configured, create **and** update reject a blank `broker_url`/`broker_vpn`/`broker_username`/`broker_password` with a 422 — the same path `sam config apply` takes.

## Event rules (the heart of the type — at least one)

Each rule says *what arrives*, *who handles it*, and *what goes back out*:

- **Match:** `name` (unique), and either `subscriptions` — one or more topics, Solace wildcards `*` and `>` supported, per-subscription `qos` (default 1) — **or** `existingQueueName`, which binds the rule to a broker queue that already exists, in consume-only mode: Agent Mesh does not create the queue, add subscriptions (the queue's owner manages them), or deprovision it on undeploy. Setting both is rejected; two rules cannot share one `existingQueueName`. `messageFormat` declares the payload encoding: `json` (default), `text`, `xml`, `raw_bytes`, `protobuf`, `structured`.
- **Filter (optional):** `eventFilter` is a deterministic test run on each message before any task starts. A message it does not match is acknowledged and dropped — no task, no model call, no cost — so a rule on a busy topic only wakes its target for the events it cares about. It is written as an invoke object: `function` plus `params.positional`, where each param is a literal (string, number, boolean, or a list of those), `"evaluate_expression(<expr>)"` reading `input.payload:<path>`, `input.topic:`, `input.topic_levels:<index>`, `input.user_properties:<key>` or `static:<value>`, or a nested `{invoke: {function, params}}`. Functions: `equal`, `not_equal`, `greater_than`, `less_than`, `greater_than_or_equal`, `less_than_or_equal`, `and_op`, `or_op`, `not_op`, `in_op` (list membership, substring, or object key), `if_else`, `subtract`, `multiply`, `divide`, `modulus`, `negate`, `power`; each takes exactly its arity (two for the comparisons and `and_op`/`or_op`, nest for more). `and_op`/`or_op` stop at the first operand that decides and `if_else` evaluates only its chosen branch. `and_op`, `or_op`, `not_op`, the `if_else` condition and the filter as a whole accept only true or false: a text, number, list or object there is an error, never read as true or false. A filter that does not compile (unknown function, wrong param count, keyword params, an expression source other than those above, a param that mentions `evaluate_expression` but is not written exactly as `"evaluate_expression(<expr>)"`, a bare `input.payload:<path>` without the wrapper, a `null` param, a NaN or infinite number param, a comparison whose params are all literals, more than 8 levels or 64 calls) is rejected when the rule is saved. A message the filter cannot decide — a field it reads is missing or null, the payload is empty, a field is read from a payload that is not a JSON object, the compared values are of different kinds (text, number, boolean, list, object; for example `equal` of a number against a text, or `in_op` of a number against a list of texts), `in_op` looks inside a number or boolean, a calculation (`subtract`, `multiply`, `divide`, `modulus`, `negate` or `power`) gives a result that is not a finite number (such as the square root of a negative number or an overflow), or something other than true or false reaches `and_op`, `or_op`, `not_op`, an `if_else` condition or the filter's answer — is **delivered, not dropped**, under every function, and logged as a warning with the rule and message id (never the payload): a filter that cannot decide must not lose a business event. The filter is a cost control, not an admission boundary: a publisher that omits the field reaches the target.

  Presence tests are `in_op` with the key as first param and an object as second: `"evaluate_expression(input.payload:)"` for a key at the top of a JSON object payload (on a text payload `in_op` searches the text for the key and on a JSON list it looks for the key among the text items, so an empty list, a list of only nulls or a mixed list like `["a", 1]` gives false when the key is not there, while a list holding only numbers, booleans, objects or lists cannot be decided and the message is delivered), `"evaluate_expression(input.payload:order)"` for a key inside a nested `order` object, or `"evaluate_expression(input.user_properties:)"` for a user property (an `and_op` of `in_op` with params `"region"` and `"evaluate_expression(input.user_properties:)"`, then `equal` on `"evaluate_expression(input.user_properties:region)"`, reads `region` only when it is present). There is no test for `null` (a null param is refused), and no test for a nested field whose parent is absent: that message cannot be decided and is delivered. A bare `input.topic_levels:` cannot be used as a whole; read one level with `input.topic_levels:<index>`. With no `eventFilter`, every message starts a task.
- **Target:** `targetAgent` **or** `targetWorkflowName` — mutually exclusive (setting both is rejected); if neither is set the rule defaults to an agent target (the built-in Orchestrator). An agent target (including the Orchestrator default) takes `promptTemplate`, the template that turns the message into the task input — it can expand the whole `{payload}`, the `{topic}`, or JSON fields like `{payload.order.id}`. A workflow target ignores `promptTemplate` and takes `inputExpression` instead — set it on every workflow rule, or the workflow receives empty input; `"input.payload:"` delivers the payload as the workflow's text input (`workflow.input.text`) — a payload that parses as JSON is re-serialized as JSON text (not as addressable fields), any other payload passes through as-is. **Exception: a workflow that declares an `input_schema`.** The workflow reads a JSON object payload as its input fields (`workflow.input.<field>`), unless the schema also accepts the payload as `workflow.input.text` and the object fails the schema or names a field the schema does not declare. A payload the schema accepts neither way fails the run before any node runs — a rule with no `inputExpression`, whose input is empty, fails a schema that has `required` fields. `structuredInvocation` attaches input/output JSON Schemas to an agent target (the agent validates and retries); a workflow target ignores it and applies its own `input_schema` (its `output_schema` is not checked).
- **Identity:** `defaultUserIdentity` (static, e.g. `order_event_user`) or `userIdentityExpression` (per-message). This is what RBAC and audit attribute the task to — don't leave it implicit for production rules.
- **Acknowledgment:** `acknowledgmentPolicy.mode` = `on_receive` (default — ack when the message arrives) or `on_completion` (ack only after the task finishes; `timeoutSeconds` default 300). A task whose result is published is acked — including a failed workflow run whose failure is published, which is never nacked, so a deterministic failure is not redelivered forever. `onFailure` applies only when the task returns a JSON-RPC error, the result fails to publish, the timeout fires, or the event can't be turned into a task (a target or input expression fails, its identity is rejected, the caller lacks permission to invoke the target, or submission otherwise fails); its `nackOutcome` (`rejected`/`failed`) is *intended* to select drop vs redeliver, though the runtime currently nacks the message the same way for both. Choose `on_completion` when losing a message on task failure is unacceptable.
- **Outputs:** `successOutput` and `errorOutput`, each with `enabled`, `topic` (`topicType` `static`, or `dynamic` for an expression-built topic), and `responseType` (`text` final text — the success default, `full` entire response, `structured` — the response's `structured_output`: an agent target's schema-validated result when the rule sets `structuredInvocation` (the success default for such a rule; only `structured` carries the validated object, `text` is empty and `full` holds just a reference to it), or a workflow target's result; `error` — the error-output default; or `custom`). An output publishes **only when `enabled: true`**; without it the block is ignored and nothing is published. A `dynamic` topic expands `{{text://…}}` blocks evaluated against the task's response: `input.payload:<field>` reads the response (`text`, `structured_output`, …), and `user_data.forward_context:<key>` reads a value the rule's `forwardContext` captured from the inbound message — the only way to put an inbound field into the reply topic. A single-brace placeholder such as `orders/processed/{id}` is published literally. For a workflow target, publish its result with `responseType: structured` (or `custom` with `customExpression: input.payload:data[0]`), and give `errorOutput` its own `responseType` (`text` or `error`). `errorOutput` receives, for any target, an error response (the agent or workflow returned an error instead of a result — for example the agent's `required_scopes` are not met, the model call fails, or the target stops responding and the task times out; the acknowledgment `timeoutSeconds` only settles the message — the task keeps running and its result is still published) and a `userIdentityExpression` that resolves to nothing while the rule sets no `defaultUserIdentity`; and a failed, rejected or canceled run of a workflow target or of a structured invocation. An agent target without `structuredInvocation` publishes every final result on `successOutput`, even a run marked failed after a tool failure the agent recovered from. An event the entrypoint can't turn into a task (a target or input expression fails, the caller lacks permission to invoke the target, or submission otherwise fails) is not published on either output — except that unresolved `userIdentityExpression`, which goes to `errorOutput`. If the user wants the result somewhere other than a topic (a DB), that's a connector on the agent/workflow side, not an entrypoint output.
- **Delivery and headers (YAML only, not in the web UI form):** an output publishes a direct message carrying only the payload unless it sets `deliveryMode: guaranteed` (wait for the broker's acknowledgement; a failed publish follows `onFailure`), `headers` and `userProperties`. `headers` takes the Solace Micro-Integration header names: `solace_dmqEligible`, `solace_timeToLive` (ms) and `solace_expiration` (epoch ms, passed to consumers unchanged; the broker does not expire on it) — these three are rejected unless `deliveryMode: guaranteed` — plus `solace_priority` (0-255), `solace_correlationId`, `solace_applicationMessageId`, `solace_applicationMessageType`, `solace_senderId`, `solace_sequenceNumber` and `solace_httpContentEncoding`. `solace_isReply` and `solace_senderTimestamp` are rejected: the entrypoint cannot set them. A header or user-property value is a literal, or a template when it contains `{{…}}`, evaluated like a dynamic topic (`input.payload:<field>` for the response, `user_data.forward_context:<key>` for an inbound value the rule's `forwardContext` captured — it can read the inbound payload, topic and user properties, not the inbound Solace headers, so an inbound correlation ID header is not reachable); a template whose whole value is one `{{…}}` (or `{{text://…}}`) block and resolves to nothing or blank text leaves the header unset (with text around a block, or several blocks, a missing field is published as `<nil>`, e.g. `id-<nil>`; a `json://` block renders a missing field as `null`, which is set; inside a longer value a number of 1,000,000 or more is written as `1.234567e+06` by a `text://` block, so use `{{json://…}}` to keep its digits), and so does a value the header cannot take (text for `solace_priority`, an object for a user property): the reply still publishes and a warning names the header. `sam config apply` refuses unknown header names, out-of-range literals, a template with an unknown expression source (such as `{{text://order:id}}`), a `solace.messaging.` user-property prefix and the guaranteed-only or unsupported headers above. TTL and DMQ only take effect when the receiving queue respects TTL and has a dead message queue, and `solace_dmqEligible` is not `false` (unset means eligible). The inbound event is acked after a guaranteed reply is acknowledged only with `acknowledgmentPolicy.mode: on_completion`; with `on_receive` it is acked on arrival, so a guaranteed reply that fails to publish is lost. `sam config plan` does not run these checks; only apply does. A literal value cannot contain `{{` (it is read as a template, and `sam config migrate` warns about such runtime literals). A budget refusal is always acked, whatever the mode. Replies are at-least-once (a Guaranteed reply whose publish times out under `on_completion` with `onFailure.action: nack` redelivers the event and re-runs the task; and in any mode, a stop after publishing can make another replica process the agent's response again and publish the same reply), so consumers should de-duplicate on a value taken from the incoming event, such as a correlation ID from `forwardContext`, not on the agent's output.

## Worked shape (in words, not YAML)

"When an order event lands on `orders/new/>`, process it with the order-triage agent, publish the result to `orders/processed`" = one rule: subscription `orders/new/>` (json) → `targetAgent: order-triage` with a promptTemplate embedding `{payload}` → `successOutput` with `enabled: true` and topic `orders/processed`, plus an enabled `errorOutput` topic so errors are visible on the mesh. Decide `on_receive` vs `on_completion` from whether a dropped event matters.

## Verify

Publish a test message to a matching topic (broker Try-Me tab or any client) and watch (a) the task appear in the web UI, and (b) the success topic. Rule cross-field mistakes (an agent target without promptTemplate, both targets set) are rejected at save time with the reason. A workflow rule without `inputExpression` is not rejected — it saves, deploys, and hands the workflow empty input, so check it before applying.
