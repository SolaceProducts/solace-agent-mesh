# Connector type catalog (10 types / 18 subtypes)

Field names below are for **naming and recognition** — they are real keys from the live catalog, safe to mention to the user. Full YAML shape, nesting, and validation: `sam-declarative-config` (or create one connector in the builder UI and `sam config pull` it). The builder UI form is generated from the same schema, so the UI is always current. When the user needs an exact **tool name** (e.g. for agent instructions), the wizard's Select Tools step shows it — don't guess tool names this file doesn't state.

## Availability

`document_db`, `graph_db` and `search` are still experimental, and `web_search` is in early access (the UI shows an EARLY ACCESS badge). Every type has its own page in the Connectors section of the Agent Mesh docs.

## Approvals (`hil`)

Every type that produces tools takes `values.hil`: `{tools: {<role>: {require_approval, approval_message, show_args, timeout, require_approval_when}}}`; fields beside `tools` are defaults for every tool of the connector. The key is the tool's **role**, not the generated `<role>_<suffix>` name or a custom `tool_name`: `slack` `slack_send_message` / `slack_update`; `sql` `sql_query`; `knowledge_base` `query_bedrock_kb`; `document_db` `mongo_query` / `dynamodb_query`; `graph_db` `neo4j_query` / `neptune_query`; `search` `elasticsearch_query` / `opensearch_query`; `web_search` `web_search`; `event_mesh` each operation's `tool_name` (`event_mesh_request` by default); `api` the snake_case operation name (`deleteUser` is `delete_user`; a raw operationId is refused); `mcp` the server's registered tool names. An unknown key you write is refused at save (except `mcp`, which is checked when the agent starts, and an `api` connector whose spec the platform cannot read, covered below), as is a `null` approval field (including `require_approval_when` and `tools`); for the role-keyed types and `event_mesh`, a stored key the save didn't change that no longer names a tool is removed with a warning, while for `api` only a spec upload that drops the operation removes its gate (with a warning), and a stored key the spec at `specification_url` lacks is kept and warned about. Leaving `hil` out keeps the stored gate, writing it replaces the whole block, and `hil: {}` removes it (`hil: null` removes it in `sam config apply` and the Builder, but a raw API call keeps the gate). For `api`, deselecting a gated operation keeps its gate, uploading a spec that drops one removes that gate and the Connectors page and `sam config apply` show the warning, and for an `api` connector that uses `specification_url` the platform reads the spec at that URL when you save and refuses a key you write that names no operation. When it cannot read or parse the spec (the URL is not reachable from the platform, or the spec has an external `$ref`) the save only warns, and a key that names no operation then stops every agent bound to the connector from starting, or leaves the gate unapplied when an agent selects operations with an `allow_list`. Renaming or removing a gated `event_mesh` operation removes its gate with a warning unless the same save writes a different `hil` block; `sam config apply` fails the plan when the manifest's `hil` still names the old operation. The gate applies to **every agent using the connector**, and workflow `tool` nodes bound to it run without asking, so route a tool that needs approval through an agent node. Full shape: `sam-declarative-config` (connector kind).

## `sql` — postgres · mysql · mariadb · mssql · oracle

Agent gets a SQL query tool: the agent's LLM writes the SQL and the tool executes it against your database. The tool introspects the schema on startup and samples up to 100 rows per table into the tool description so the LLM knows the shape. **This is not tunable from a connector** — the connector emitter hard-codes the tool's config, so `auto_detect_schema` / `schema_summary_override` / `schema_sample_size` set as connector values are silently ignored. Those keys are real, but only on a hand-authored `execute_sql_query` built-in tool entry, which is a different (non-connector) authoring path. Fields: `hostname`, `port` (defaults 5432 / 3306 / 3306 / 1433 / 1521), `database`, `username`, `password`. Oracle uses `service_name` instead of `database`. MSSQL adds `encrypt` (yes / no / strict) and `trust_server_certificate`. **The tool can run any SQL the credentials allow — use a read-only DB user scoped to the needed schemas** (the UI shows this warning; repeat it).

## `knowledge_base` — bedrock

RAG retrieval from an Amazon Bedrock Knowledge Base. Fields: `kb_id`, `region`, then `auth_type`: `access_key` (`aws_access_key_id` + `aws_secret_access_key`) or `iam` role chaining (`aws_account_id` + `role_name`, optional `session_name`, optional `external_id` for cross-account). IAM permissions: `bedrock:Retrieve` and `bedrock:GetKnowledgeBase` on the KB.

## `api` — openapi

Every operation in an OpenAPI 3.x spec becomes an agent tool (operations without an `operationId` still appear, with a generated name). Spec via `specification_url` **or** file upload; `base_url` is required and overrides the spec's `servers`. Before authoring (UI or declarative), collect: the spec source, the `base_url`, and the auth scheme + where the credential goes (header/query and its name) — the user's message rarely contains all three. Options: `custom_headers`, `allow_list` (comma-separated operation IDs). `auth_type`: `none` | `apikey` (header or query: `auth_apikey_location`, `auth_apikey_name`, `auth_apikey_value`) | `http` (basic or bearer) | `oauth` (authorization/token URLs, client id/secret, scopes, `auth_oauth_token_endpoint_auth_method`, and `auth_oauth_pkce`: `enabled` by default, so each sign-in carries a PKCE S256 challenge; set `disabled` only for a provider that rejects PKCE, such as Atlassian Cloud, and never with method `none`, which the platform refuses). Each OAuth connector keeps its own sign-in per user, labelled with the connector's name, so an agent can use OAuth connectors to several systems. The UI can auto-detect the auth scheme from the spec. The Platform service fetches `specification_url` itself, ignoring proxy settings and refusing private-network addresses unless the operator sets `SAM_PLATFORM_ALLOW_PRIVATE_MCP` to `true`. The opt-out is process-wide: anyone who can view connectors can then reach internal addresses through these fetches, so recommend it only for trusted users.

⚠️ **A file embed reaches this target as text, not bytes.** The calling side resolves *early* embeds only; `artifact_content` is a **late** embed, so it is passed through untouched and each tool resolves it during its own execution. A plain REST endpoint cannot, so it receives the literal embed string. **Use a tool that resolves the embed** — there is no way today to get artifact bytes into an `api` connector call. In particular, do not reach for a `multipart/form-data` binary parameter: the connector's artifact-resolution path for multipart fields exists in the code but is not wired to anything, so an `artifact://` value fails the call outright with *"artifact URI … provided but no artifact service available"*.

⚠️ **A spec that never arrived still deploys.** With neither an uploaded spec nor an external spec URL, the connector is built with an unresolvable spec reference. It does not fail the deploy: the agent starts and **registers no tools from this connector at all**, so the model never sees them and there is no failing call to trace. The signals are two error log lines — one when the connector's config is built, one when the agent starts and finds no spec to load — plus a failed registration status carried back against the connector, so the connector's own card is the fastest place to see it. After creating or updating an `api` connector, confirm its tools actually appear rather than assuming a clean deploy means the spec landed. (Binding such a connector to a workflow `tool` node is the one loud case — that fails the deploy outright.)

## `mcp` — remote

Exposes a **remote** MCP server's tools to the agent — SSE or streamable HTTP only (`server_url`, `connection_type`); **there is no stdio/command subtype**. If the user's MCP server only runs locally via stdio, that is not a connector. The Platform service discovers tools from `server_url` itself, ignoring proxy settings and refusing private-network addresses unless the operator sets `SAM_PLATFORM_ALLOW_PRIVATE_MCP` to `true` (process-wide: anyone who can view connectors can then reach internal addresses, so recommend it only for trusted users). When a save has no `manifest`, the Platform service lists the server's tools then; if that fails, the connector is still saved without tools and the response carries a warning with the reason, which `sam config apply` prints under the connector's row. `auth_type`: `none` | `apikey` | `http` | `oauth` (`auth_oauth_mode`: `discovery` or `manual`). Tool selection: at most one of `tool_name` (exactly one tool) / `allow_list` / `deny_list` — colliding gives *"tool_name, allow_list, and deny_list are mutually exclusive — got …"*. A `manifest` may not be combined with any of those three, because the manifest **is** the registered tool set: *"manifest is mutually exclusive with `<field>` — the manifest already declares the tool set"*. **`selected_tools` is the exception and works the opposite way — it *requires* a manifest** (*"selected_tools cannot be used without a manifest…"*), its names must appear in that manifest, and an empty string is rejected; omit the key to select all. `tool_name_prefix` is orthogonal to all of this. Also available: `hil` (per-tool human-in-the-loop approval gating, keyed by the registered tool names), and `ssl_config` for a server behind mutual TLS or a private CA — a nested map with `ca_bundle`, `client_cert`, `client_key` (set both or neither) and `server_name`. The web UI has no TLS fields, so set and change it only declaratively or through the API. An update that leaves `ssl_config` out, including a save in the web UI, keeps the stored block; `ssl_config: {}` (or `null` in a `sam config apply` file) removes it. The three file fields are absolute, clean paths to PEM files (the key unencrypted), not PEM content, and each must lie inside the directory the operator sets in `SAM_MCP_CONNECTOR_TLS_DIR` on the Platform service, which refuses the connector otherwise. The same files must exist at the same paths on the Platform service's host (it presents the certificate during tool discovery) and the agent's host (tool calls). With the Helm chart, the operator sets `samDeployment.mcpConnectorTLS` (`enabled`, `secretName`), which mounts one Secret of PEM files at `/etc/sam/mcp-tls` on both pods and sets the variable. `verify` is refused: only the operator turns certificate checks off, with `SAM_MCP_CONNECTOR_TLS_VERIFY=false`.

**OAuth MCP servers need a `manifest`.** By default the agent discovers tools by calling the server's `tools/list` when it starts. Delegated OAuth blocks that call (401 until a user signs in), and **no user is present at agent startup** — so without a manifest the agent boots with **zero tools**. Which auth types this actually applies to:
- `connection_type: streamable-http` (the default) + `auth_type: oauth` → **hard requirement**: the runtime refuses to register the client without a manifest (*"streamable-http server with auth requires a manifest; tools/list is blocked until the user completes OAuth — either provide manifest/manifest_file or switch to an SSE transport"*).
- `connection_type: sse` + `auth_type: oauth` → the runtime does **not** block it; the fail-fast guard is streamable-http only, and its own error text offers SSE as the alternative to a manifest. Startup discovery still 401s, so a manifest remains the safer choice if tools come up empty.
- `auth_type: apikey` or `http` → **no manifest needed.** Those credentials are emitted as static request headers (or a URL query param), so they ride on the startup `tools/list` and discovery succeeds with no user present. Don't prescribe a manifest here — it would force you to drop `allow_list`/`deny_list`/`tool_name` for nothing.
- **`sam config apply` / deploy SUCCEEDS either way** — the connector saves, the agent deploys "successfully," and only at *runtime* does the connector show **0 tools**. Deploy-success ≠ working tools; verify the tool count.

So for an MCP connector with `auth_type: oauth`, supply an inline `manifest`: a list of entries, each with `name`, `description`, an optional `inputSchema`, an optional `outputSchema`, and an optional `annotations` map holding the server's `readOnlyHint`, `destructiveHint` and `openWorldHint` booleans as its `tools/list` reports them (these are the server's claims, recorded as hints and shown in discovery; a connector's tools stay side-effecting at runtime, because a hint makes a tool read-only only on an inline `tool_type: mcp` agent entry that sets `trust_annotations: true`, and a `destructiveHint: true` or `openWorldHint: true` always counts as side-effecting, an omitted `openWorldHint` counting as `true` like the MCP default). The `outputSchema` is honoured by the runtime: its top-level `properties` name the fields a workflow addresses as `{{node.output.mcp_structured_content.<field>}}`, and a reference they do not name is reported as unverified when the workflow starts. Supply it whenever the server publishes one — on this path there is no live `tools/list` to discover it from. Get the tool list by running the builder's Select-Tools / discovery step **after** entering credentials, or from the server's published tool list, then carry those entries as the `manifest`. With a manifest the agent advertises the tools at startup and the per-user OAuth flow runs on first tool call. The manifest also lets you pin/restrict exactly which tools register, as long as it stays in the connector's YAML: an update that leaves `manifest` out makes the platform list the server's tools again and store that list in its place. When the server is unreachable or lists no tools, the stored list stays and the save warns. An OAuth connector is never listed at save: an update that leaves `manifest` out keeps its stored list without a warning, and one that sends an empty `manifest` clears it and the save warns, because its agents then start without its tools. Full YAML shape: `sam-declarative-config`.

**Adding a `manifest` to an existing connector — the atomic-PATCH trap.** `sam config apply` sends the connector's `name` + `description` + `values` (the manifest is inside `values`) as **one** `PATCH /api/v2/platform/connectors/{id}`. The server validates the whole body; a failure on *any* field returns a 4xx and **nothing in `values` persists** — for an `mcp` connector `updatedTime` never advances and the agent stays at 0 tools. (The one type where `updatedTime` can move on a failed apply is `api`/`openapi`: its `specification_file` goes up in a separate `PUT .../{id}/resource` before the PATCH and stays persisted regardless.) The classic misdiagnosis is "the reconcile diff ignores the manifest" — it does **not**; `sam config plan` correctly shows the `~ <connector> update`. What actually happened is a sibling field was rejected. Two common culprits. First, **tool-selection exclusivity**: adding a `manifest` to a connector that already has `allow_list`, `deny_list`, or `tool_name` is rejected outright — remove those when you add the manifest. Second, **length**, enforced on update in both directions identically to create (`name` only when it changes): `name` 3–255 and `description` 10–1000. A description that quietly grew to 1001 chars fails with 422 *"description must be at most 1000 characters"*, and one trimmed to 9 chars fails with *"description must be at least 10 characters"* — either takes the bundled manifest down with it. (A field left out keeps its stored value; an empty one is rejected too.) Diagnosis order when a manifest "doesn't take": (1) strip any `allow_list`/`deny_list`/`tool_name` from the same connector; (2) confirm `apply` actually reached the server — a wrong `--url`/port yields connection-refused that hides the real 422; (3) read the apply output for a 4xx on a sibling field (description/name length, or a changed `name` that fails the create rules, including `safename`; an unchanged stored name is kept as it is, and `safetext` runs on create only); (4) fix that field and re-apply — the manifest then persists and `updatedTime` moves. Verify with the runtime tool count, not deploy success.

**Discriminator:** user already runs an MCP server the agent should consume → this type. User wants to *expose* Agent Mesh agents to MCP clients → MCP entrypoint (`sam-entrypoints`). One-agent inline MCP wiring exists in runtime YAML, but the connector is the taught path. A workflow `tool` node can also bind this connector: `connector: <name>` plus `tool: <server tool name>` (`sam-author-agent`, workflows reference).

## `slack` — bot

Outbound posting: a send-message tool and an update-message tool (text/Markdown, threads, attachments, Block Kit). **The channel is a tool-call parameter, not connector config** — the agent supplies a channel ID, `#channel-name`, user ID, or user email per call; tell the agent its target channel in its instructions. Single config field: `slack_bot_token` (a bot token, `xoxb-…`; the schema recommends `chat:write`, `files:write`, `users:read`, `users:read.email`; invite the bot to the channel, or grant `chat:write.public` to post to public channels without joining). **Inbound** — people chatting with agents from Slack — is the Slack *entrypoint*. Machine-triggered notifications → this connector.

## `event_mesh` — solace

The agent sends requests to backend services over a Solace broker. The broker connection is **required and custom** — all four of `broker_url`, `broker_vpn`, `broker_username`, `broker_password` (credentials are never inherited from the Agent Mesh broker). Unique among connectors: **you define the tools** — an `operations` array where each operation becomes one agent tool with `tool_name` + `tool_description` (what the LLM sees), a `topic` template with `{property_name}` placeholders (legacy `{{ param }}` still parses), `payload_format` (json/yaml/text), request/reply (`wait_for_response: true`, `request_expiry_ms`) or fire-and-forget, and an `input_schema` (JSON Schema) parameter declaration. Inbound (a mesh topic triggering an agent) → eventmesh entrypoint.

## `document_db` — mongodb · dynamodb *(experimental)*

MongoDB: `scheme` (`mongodb` / `mongodb+srv`), `hostname`, `port` (default 27017; ignored for `mongodb+srv`), `username`, `password`, optional `database`, required `collection`, optional `options`. DynamoDB: `region`, `table_name`, `auth_type` `access_key` or `iam` (`role_arn`, optional `session_name` / `external_id`). This — not a third-party MCP server — is the product path for "let the agent look up records in Mongo/DynamoDB".

## `graph_db` — neo4j · neptune *(experimental)*

Neo4j: `scheme` (`neo4j` / `neo4j+s` / `bolt` / `bolt+s`), `hostname`, `port`, `username`, `password`, optional `database`. Neptune: `scheme`, `hostname`, `port`, `region`, AWS `auth_type` access_key or iam (`role_arn`).

## `search` — elasticsearch · opensearch *(experimental)*

Elasticsearch: `scheme`, `hostname`, `port` (or Elastic Cloud `cloud_id`), plus `api_key` (or `username` / `password`). OpenSearch (managed domain or Serverless): `scheme`, `hostname`, `port`, `region`, AWS `auth_type` access_key or iam. **Subtype ≠ vendor:** the `opensearch` subtype is specifically AWS-managed OpenSearch (domain/Serverless, AWS-auth); a **self-hosted** OpenSearch cluster speaks the Elasticsearch-compatible API, so use the `elasticsearch` subtype for it. On Serverless (`.aoss.amazonaws.com`), delete works by document id only (no delete-by-query), and update or index with an explicit id works only on search collections.

## `web_search` — tavily · exa *(early access)*

Gives every attached agent one cited web search tool: results the agent cites show as numbered citations in the chat. Not the `search` type, which queries the user's own Elasticsearch/OpenSearch. It replaces the `web_search_google` built-in and gives `deep_research` a search provider, because the Google Custom Search API they use shuts down on 2027-01-01. Setup is pick a provider, paste its API key, save. Fields: `api_key` (secret), `api_base` (optional; omitted, the connector uses `https://api.tavily.com` / `https://api.exa.ai`; set it only for a private mirror or proxy; must be an absolute http(s) URL with a host and no user name or password; an update that changes `api_base` must also set `api_key`, because the stored key is never sent to a new address), `max_results` (1–20, default 5), `safe_search` (`"yes"` / `"no"`, default `"no"`). Tavily offers image search, recency and domain filters; Exa offers recency and domain filters, no image search.

- **Tool name:** `web_search_<last 8 hex digits of the connector id>`, so several Web Search connectors on one agent give distinct tools. Optional `tool_name` overrides it but must match `web_search_[a-z0-9_]+`, be at most 64 characters, and not be a built-in tool name such as `web_search_google`, or the save is refused; optional `tool_description` replaces the default description of what the tool does (the citation rules stay).
- **Runs in the STR** (MCP connector tools run in their MCP server and OpenAPI ones in the AWE). The STR needs outbound HTTPS to the provider, or to `api_base`. The agent turns the tool's results into citations in the chat.
- **Key check on save.** The platform runs one single-result test search. A key the provider rejects blocks the save (*"Tavily rejected the API key…"* / *"Exa rejected the API key…"*). A rate, plan or credit limit, any other HTTP status, or the platform not reaching the provider (including a private-network `api_base`, which the platform does not contact) saves with a warning, because the platform's network path is not the agents'. A key that reaches the platform as a placeholder (`<<__SAM_REQUIRED__>>`) or a literal `${...}` is not checked; `sam config apply` substitutes `${VAR}` before it sends the connector, so an applied key is checked.
- **Billing:** the provider bills each search to the key, and every agent attached to the connector shares the key and its plan limits.
- **Agents only.** Workflow `tool` nodes are not offered its tool; route web search in a workflow through an agent node.
- **Deep research.** An agent that also has the research toolset (`builtin_research_tools`) runs `deep_research`'s web searches through the connector: its provider, key and `api_base` replace any Google Custom Search keys in the tool's `tool_config`, its `safe_search` applies unless the tool's own config already turns safe search on or holds a value that is neither true nor false (safe search then stays on), and the tool's other settings stay. The connector's `hil` approval gate does not apply to these searches. With several Web Search connectors on the agent, `deep_research` uses the one with the earliest **Created** time (lowest **ID** on a tie; both show in the connector's details in the UI), so give an agent that uses `deep_research` exactly one Web Search connector. These searches run in the AWE, not in the STR, so the AWE also needs outbound HTTPS to the provider, and an AWE older than the release that added Tavily and Exa to `deep_research` fails them with an error that starts with "Google Search API key and CSE ID must be configured".
